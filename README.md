# Email Triage Agent (Groq + LangChain)

A Python AI agent that parses emails and produces a **structured and validated triage**: category, priority, sentiment, summary, suggested action, and an optional response draft. It uses a **free** Groq LLM model via **LangChain**, along with `PydanticOutputParser` to ensure the output is always returned as validated JSON — never loose text.

The agent can run completely offline (on sample emails) or connected to your real email account via IMAP/SMTP, featuring safety guardrails that prevent any message from being sent automatically.

## How it works

1. An email (either a sample or fetched from the server) is converted into plain text.
2. This text is injected into a prompt along with format instructions generated by `PydanticOutputParser`.
3. The Groq model processes the prompt and returns a JSON.
4. The `PydanticOutputParser` validates this JSON against the `EmailTriage` schema. If the JSON is malformed, the `OutputFixingParser` makes a second call to the model to fix it automatically.
5. The strongly-typed result is displayed in a readable format; optionally, a response draft can be sent after human confirmation.

The complete flow:

```
email --> plain text --> prompt (+ format_instructions) --> Groq LLM --> JSON
       --> PydanticOutputParser (+ OutputFixingParser) --> validated EmailTriage

```

## Architecture

The project follows a layered architecture with decoupled responsibilities:

```
src/main.py            CLI and operation mode orchestration
   │
   ├── src/chain.py        LCEL pipeline: prompt | llm(Groq) | parser
   ├── src/email_client.py Email I/O: IMAP (read) + SMTP (send)
   ├── src/models.py       Pydantic schemas: EmailTriage + EmailMessage
   ├── src/prompts.py      Triage prompt template
   └── src/config.py       Configuration loading/validation (.env)

data/sample_emails.py  Sample emails for offline mode
tests/                 pytest suite (no real network calls)

```

Design principle: **`email_client` knows nothing about AI, and `chain` knows nothing about IMAP**. They communicate exclusively through plain text, orchestrated by `main`. This keeps the AI core isolated and testable, allowing you to swap the email layer (or the model) without touching the rest of the code.

The `llm` is passed to the chain via **dependency injection** (`build_triage_chain(llm)`), which allows injecting a mock model during tests to avoid depending on the real API.

## The output contract (EmailTriage)

Every triage produces a validated object with the fields below. Fields with fixed values use **Enums**, forcing the model to choose from a closed set and drastically reducing invalid outputs.

| Field | Type | Possible Values |
| --- | --- | --- |
| `category` | Enum | `support`, `sales`, `finance`, `spam`, `personal`, `other` |
| `priority` | Enum | `urgent`, `high`, `medium`, `low` |
| `sentiment` | Enum | `positive`, `neutral`, `negative` |
| `summary` | text | 1-2 sentence summary |
| `suggested_action` | Enum | `reply`, `forward`, `archive`, `ignore` |
| `response_draft` | text or `null` | Populated only when the action is `reply` |

*Note: The keys and values above reflect the English translation. In the original Portuguese code, these map to `categoria`, `prioridade`, `sentimento`, etc.*

Example output (JSON produced by the model, already validated):

```json
{
  "categoria": "suporte",
  "prioridade": "urgente",
  "sentimento": "negativo",
  "resumo": "Cliente relata que o sistema está fora do ar em produção.",
  "acao_sugerida": "responder",
  "rascunho_resposta": "Olá, obrigado por avisar. Já estamos investigando..."
}

```

## Installation

```bash
cd email-triage-agent
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

```

### Note for Debian/Ubuntu environments

If the `python3 -m venv` command fails with `ensurepip is not available`, the venv package is not installed. You have two options:

Option A (recommended), install the venv package:

```bash
sudo apt install python3-venv    # or python3.12-venv depending on your version

```

Option B, without admin privileges, create the venv without pip and install pip manually:

```bash
python3 -m venv --without-pip .venv
curl -sSL https://bootstrap.pypa.io/get-pip.py -o /tmp/get-pip.py
.venv/bin/python /tmp/get-pip.py
.venv/bin/pip install -r requirements.txt

```

## Configuration (.env)

Copy the template and fill in the values:

```bash
cp .env.example .env

```

Available variables:

| Variable | Required | Default | Description |
| --- | --- | --- | --- |
| `GROQ_API_KEY` | Yes (for triage) | — | Groq API Key |
| `GROQ_MODEL` | No | `llama-3.3-70b-versatile` | Groq model to use |
| `EMAIL_ADDRESS` | Yes (Phase 2) | — | Your email address |
| `EMAIL_APP_PASSWORD` | Yes (Phase 2) | — | App Password (not your real password) |
| `IMAP_SERVER` | No | `imap.gmail.com` | IMAP server for reading |
| `IMAP_PORT` | No | `993` | IMAP port (SSL) |
| `SMTP_SERVER` | No | `smtp.gmail.com` | SMTP server for sending |
| `SMTP_PORT` | No | `587` | SMTP port (STARTTLS) |

Email credentials are optional for Phase 1: the `--demo` mode runs with just the `GROQ_API_KEY`. Email credential validation only happens when you use modes that connect to the server.

Common servers for other providers:

| Provider | IMAP | SMTP |
| --- | --- | --- |
| Gmail | `imap.gmail.com:993` | `smtp.gmail.com:587` |
| Outlook / Office 365 | `outlook.office365.com:993` | `smtp.office365.com:587` |
| Yahoo | `imap.mail.yahoo.com:993` | `smtp.mail.yahoo.com:587` |

## How to get credentials

### Groq Key (free)

1. Go to [https://console.groq.com](https://console.groq.com?utm_source=gemini) and create an account.
2. Generate an API key in the dashboard.
3. Paste it into `GROQ_API_KEY` in your `.env`.

### Email App Password

Modern providers block IMAP/SMTP logins with your standard password. Always use an App Password.

For Gmail:

1. Enable 2-Step Verification: [https://myaccount.google.com/security](https://myaccount.google.com/security)
2. Generate an app password: [https://myaccount.google.com/apppasswords](https://myaccount.google.com/apppasswords)
3. Copy the 16-character password (format `abcd efgh ijkl mnop`).
4. Place it in `EMAIL_APP_PASSWORD` and your email in `EMAIL_ADDRESS`.

## Usage

Always activate the virtual environment before running:

```bash
source .venv/bin/activate

```

Recommended progression, from safest to most powerful:

```bash
# 1. Offline triage on sample emails (only requires GROQ_API_KEY)
python -m src.main --demo

# 2. Fetch and triage your real unread emails (read-only, sends nothing)
python -m src.main --fetch 5

# 3. Interactive with dry-run: shows the drafts it would generate, without sending
python -m src.main --fetch 5 --interactive --dry-run

# 4. Interactive with real sending: asks for confirmation (y/N) before each send
python -m src.main --fetch 5 --interactive

```

To see the full help menu:

```bash
python -m src.main --help

```

## Operation Modes

| Flag | What it does | Connects to email? | Can it send? |
| --- | --- | --- | --- |
| `--demo` | Triages sample emails | No | No |
| `--fetch N` | Reads and triages N unread emails | Yes (read) | No |
| `--fetch N --interactive` | Triages and offers to send drafts | Yes | Yes (with confirmation) |
| `--fetch N --interactive --dry-run` | Triages and shows drafts | Yes | No |

`--demo` and `--fetch` are mutually exclusive (you use one or the other). Sending only happens in `--interactive` mode without `--dry-run`, and even then, it requires you to answer `y` for each email.

## Security

* **App Password, never the real password.** Documented above; your actual password should not be used.
* **`.env` is in `.gitignore**` — credentials never go into version control.
* **Read-only by default.** No mode sends an email unless you explicitly enable `--interactive`.
* **Mandatory human confirmation.** Even in interactive mode, the agent asks before every send. It never sends on its own.
* **`--dry-run`** allows you to review all drafts with zero risk of sending.
* **Groq rate limits.** The free tier has a requests-per-minute limit. There is a 1-second pause between emails; when processing many at once, you might hit the limit (use a smaller `N` in `--fetch`).

## Troubleshooting

| Symptom | Probable Cause | Solution |
| --- | --- | --- |
| `GROQ_API_KEY not configured` | `.env` missing or empty | Copy `.env.example` to `.env` and fill in the key |
| `Missing email credentials` | Used `--fetch` without configuring email | Fill in `EMAIL_ADDRESS` and `EMAIL_APP_PASSWORD` |
| IMAP authentication error | Used normal password instead of App Password | Generate and use an App Password |
| `ensurepip is not available` | venv package not installed | See the installation section (Option A or B) |
| Slow responses or limit error | Groq rate limit hit | Reduce `N` in `--fetch` |

## Limitations and Next Steps

Current state and known limitations:

* Tests use mocks; **an end-to-end test with real credentials has not yet been executed** (requires user Groq key and App Password).
* Body parsing only extracts the first `text/plain` part; HTML-only emails might come back empty or truncated.
* Attachments are not processed.
* Does it mark emails as read when fetching? No: it uses `BODY.PEEK`, which preserves the unread status on the server.

Ideas for evolution:

* Extract text from HTML emails (e.g., with `beautifulsoup4`).
* Batch process a CSV/mbox file and export the results.
* Add few-shot examples to the prompt to improve consistency.
* Result caching and explicit rate limit handling with backoff.
* Evaluation metrics comparing the triage against manual labels.
